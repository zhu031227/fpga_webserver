### 已知 bug 现状（细节全在 doc/日报_20260831.md 补录/补录2 + doc/项目状态.md，此处只列接手要点）

**P0 · save 偶发挂死**（3 次中挂 2 次）
- 挂死形态：HTTP/ICMP 全死、不能自愈、**仅 JTAG 固件重载可救**（`scripts/load_firmware_vivado.tcl`，bit 不用重烧，3-5 分钟）
- 已排除的方向：C 层 Flash 写超时齐全（flash_cfg.c wait_idle 50 万/busy 20 万上限）→ 挂点在 C 保护之下的总线/硬件层
- **证据修正（重要）**：旧 jcpu.tcl 的 local_time 判据无效（0x06 从未被写，恒读 0）——"CPU 核域被复位"的旧结论作废。**新判据用 `scripts/jtag/jlatch.tcl`**（写 0x06 双锁存比 delta：>0=时钟域活，=0=硬件级死亡）；delta>0 但 HTTP 死 = 软件层假死
- 挂死时已取证：boot_stage=0x12（引导后挂）、Flash 未写入、v2 A/B 保护未触发、SubBus/白名单寄存器可读
- **挂死可能不止 save 一个源**：挂死#1 = clear POST+add+3 连 GET（无 save）；#3 = 3 连 delete 重试。与 P2 的"密集请求"恶性互动
- **修法**：ILA 挂 LCPU 总线抓 save/请求序列。`ila_cap.py` + ILA 核 4/5 在 `/tmp/sfp_dbg/`（**易失目录，会话开始先把它拷进仓库 scripts/jtag/ 或备份**）；UART `/dev/ttyACM0`@921600

**P2 · API 空响应两类**
- A 类：执行了没回执（多数）；B 类：**整个请求被丢弃**（JTAG wl_ctrl 佐证状态未变）
- 8s 节奏仍 2~3 连丢，全天高频；"重试对抗空响应"会诱发挂死（恶性互动）
- 修法方向：固件主循环取证（c/designApp.c 的 eth→tcp 分发 + c/tcp.c 处理逻辑），找丢请求/丢回执的点；建议先在板上做受控复现实验（不同密度/端点/顺序）定位规律

**P3 · 页面读取走停等窗**
- `c/web_pages.c:75 FLASH_MEM_RD32`：页面 body（Flash 0x420000）逐字节走内存映射停等窗，3KB 页约 800 次读，任一次停等=挂死且软件无法加超时
- **修法模板现成**：照 `c/flash_cfg.c` v2 的 sflash 寄存器路径（SubBus 0x4000，W_HI/W_LO/W_LEN/R_WORD/IDLE/START，全部带超时）把页面读迁过去。注意页面在 0x420000、配置在 0xC20000，命令/地址组织一致

**wl_status(0x301) 无驱动**
- 寄存器已在 RTL 表里（RO，[7:0]=lookup_mode、[15:8]=used_cnt），全工程无人驱动 → 读数恒 0，无法区分"正常"和"断线"
- 修法：rtl/ 侧（mac_whitelist_top 或 reg_webserver 读 mux）接上真实信号 + 可选在 /api/wl/status 里带出。模式 2 集成时必修，现在修正好

## 二、工作纪律（今天实测教训）

1. 所有 curl 加 `--interface wlp4s0`（管理走 WiFi，eno1 走数据通路会被白名单拦）
2. POST 后**必须读回确认**；请求间隔 ≥2s（最好 8s）；**不要密集重试**——会诱发挂死
3. 修固件流程：`cd c_build && make PLATFORM=xilinx riscv_reset_addr=0xf TCL_BASE=0x8000` → `vivado -mode batch -source scripts/load_firmware_vivado.tcl`（bit 不动）；提交跳过 `c/inc/build_time.h`
4. 板离线（掉电）恢复：README Quick Start B 档——`scripts/program_bit_vivado.tcl -tclargs <v0008.bit>` + `load_firmware_vivado.tcl`（**勿用 openFPGALoader，IDCODE 误读**）
5. Vivado 批处理统一 `-nolog -nojournal`；JSON 验证用 `python3 -m json.tool`
