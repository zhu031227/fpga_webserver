## 发现的问题（按严重度）

### P0 · POST /api/wl/save 必挂 CPU（两次复现）
- **现象**：save POST 一发即死——首次连接层超时（HTTP 000），之后 HTTP 永久无响应；不能自愈，仅 JTAG 固件重载可恢复
- **取证**：
  - `local_time(0x07/0x08)`（**硬件 RO 自由计数器**）冻结 0 → **CPU 核所在域被复位/停钟**，非软件死循环
  - `boot_stage(0x12)=0x12`（引导成功后才挂）；
  - `wl_ctrl(0x300)`/`e2_txok=569`/`drop=419` 均读数正常 → JTAG-AXI 桥、SubBus 总线、白名单硬件全部存活，**仅 LCPU CPU 域死**
  - 挂死后重载固件：`boot_stage=0x12` 且加载内容为旧配置 → **Flash 实际未写入**（死在擦除前/中），v2 A/B 保护未被触发，引导安全
- **矛盾点**：C 层写路径超时齐全（`flash_cfg.c` sflash_wait_idle 50 万次 / flash_wait_busy 20 万次上限）→ 挂点在 C 超时保护之下的总线/硬件层，**需 ILA 跟 LCPU 总线定位**
- **历史关联**：08-30 12:58 毒扇区假死案（v1 固件）同样由 save 触发。**save 是一贯的杀手，v2 健壮化只救了引导读，没救 save**

### P1 · /api/wl/diag 返回非法 JSON
- `whitelist_hw_diag()`（c/whitelist.c:233）拼 `r`/`t2`/`t5`/`t12`/`t13`/`f` 六个顶层节，**节与节之间无逗号**，`python -m json.tool` 校验失败

### P1 · diag 每次调用污染白名单硬件表
- T4 自测写 entry12（CA:FE…）后用 `cfg_mac==0` 的 WR 触发删除，**当前 RTL 不支持该删除路径**（t12 回读 dv=1 仍 valid）→ 每调一次 diag 留下 **idx12 全零 MAC 幽灵条目**，HW used=1 vs SW used=0 分歧
- 实测时间线：diag 调用前 hwlist used=0，调用后 used=1（idx12 零 MAC），重试稳定复现
- 幽灵条目固件重载后消失 → 逐槽写路径可清，bulk CLEAR 对其无效（或当时 clear POST 本身被丢弃，见 P2）
- **临时规避：在 RTL 支持前不要调用 /api/wl/diag**

### P2 · LCPU API 空响应分两类（此前未知）
- **A 类：执行了没响应**（多数）：操作生效，仅回执丢失
- **B 类：整个请求被丢弃**：实测 BB:BB:BB:BB:BB:02 add 空响应后列表无痕，重试才成功——**客户端无法判断操作是否生效**（配置 API 语义缺陷；页面靠操作后强制刷新列表部分兜底）
- 空响应与请求密度强相关：密集连发 3 连 GET 可全部空响应；间隔 ≥2s 时明显减少

### P3 · 结构性风险：页面 body 仍走 flash_mem_reader 停等窗
- v2 重构把**配置读**（0xC20000）迁到了可超时的 sflash 寄存器路径，但**页面内容**（0x420000）仍逐字节走内存映射窗：`web_pages.c:75 FLASH_MEM_RD32`，3KB 页面约 800 次窗口读，任一次停等即挂死且软件无法加超时
- 本次两次页面抓取均成功，窗口多数时候正常，但属结构性隐患
